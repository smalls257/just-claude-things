# Manual integration testing for Phase-2

Phase-2 is a Markdown skill playbook, not executable code. Test it by
running the full `scaffold-with-guardrails` skill against each fixture in
a throwaway directory and verifying the output.

## Per-fixture expected behavior

| Fixture | Expected Phase-2 behavior |
|---|---|
| `valid-single-module.md` | Pre-check passes silently. Emits 9 files for Orders + 1 SQL migration. Build succeeds. |
| `valid-multi-module.md` | Pre-check passes silently. Emits files for Customers + Orders modules. Shared module has no entities-with-DDL (Money is documentation-only), so no generated row type or migration entry. Build succeeds. |
| `malformed-unclosed-module.md` | PREREQ-CHECK fails before Phase-1 even runs. Error message references TECH-DESIGN-TAGS.md. |
| `cross-module-ref.md` | PREREQ-CHECK passes (tags are well-formed). Phase-2 pre-check P3 rule 3 fails. Gap report names "Orders.Order.customer references cross-module entity Customers.Customer". User prompted fix/proceed. |
| `missing-contract.md` | PREREQ-CHECK passes. Phase-2 pre-check P3 rule 1 fails. Gap report names "Endpoint Orders.POST /orders/items references undefined DTO LineItem". User prompted fix/proceed. On `proceed`, the POST /orders/items endpoint emits with `object` placeholder for its Request type. |
| `no-tags.md` | PREREQ-CHECK passes (no tags to validate). Phase-1 completes. Phase-1 → Phase-2 handoff scans for tags, finds zero, prints "Phase-2 skipped" note. Exits cleanly. |

## Procedure for each fixture

1. `mkdir -p /tmp/phase2-test-{fixture-name} && cd /tmp/phase2-test-{fixture-name}`
2. `git init`
3. `cp /path/to/repo/skills/scaffold-with-guardrails/test-fixtures/{fixture}.md docs/tech-design/{slug}.md`
   (Slug from the fixture's frontmatter.)
4. Invoke `scaffold-with-guardrails` skill. Pass slug when prompted.
5. Observe behavior — compare against the table above.
6. List output tree: `find . -type f -not -path './.git/*' | sort`
7. For success cases, the file list should match the corresponding
   "Files generated" lines in `test-fixtures/expected/{fixture-name}/`
   (see below for snapshot format).
8. `rm -rf /tmp/phase2-test-{fixture-name}`

## Golden-output snapshot format

For each success-case fixture (`valid-single-module`, `valid-multi-module`),
maintain a snapshot directory at
`test-fixtures/expected/{fixture-name}/` containing:

- `files.txt` — sorted list of files Phase-2 emits (relative paths)
- `Order.cs`, `OrderRow.cs`, etc. — verbatim copies of expected file
  contents

When you change Phase-2's prompts (Tasks 4-8), re-run the affected
fixtures and diff the actual output against the snapshot. If the diff
looks correct, update the snapshot. If unexpected, revisit the prompt.

This is **manual diff workflow** — no CI automation. Phase-2 is
LLM-driven; deterministic byte-equality is not guaranteed across runs,
but structural equality (same files, same skeleton shape) should hold.

## What to check on every run

Beyond per-fixture expectations:

- Every generated `.cs` file starts with the three-line `// Generated by
  scaffold Phase-2` header.
- Every generated `.cs` file's namespace matches its directory.
- No file references a type the build cannot resolve (run `dotnet build`).
- Test stubs use `[Fact(Skip = "TODO: ...")]` so a fresh scaffold's
  `dotnet test` exits green. Endpoint handler bodies throw
  `NotImplementedException("TODO: implement {METHOD} {PATH}")`.
- The migration file lists all entities from all modules in module-then-
  entity order.
